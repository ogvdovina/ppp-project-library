# Библиотека проектов ГЧП — правила работы

## Проект

Учебный сайт с каталогом проектов ГЧП ВВБ, фильтрами и страницами проектов.
Интерфейс и пояснения пользователю — на русском. Делай простой, наглядный
продукт для живой демонстрации. Точные функции и критерии находятся в GOAL.md.

## Контекст

В начале задачи прочитай GOAL.md, STATUS.md, README.md, если он существует,
и указанный пользователем план из plans/.

- GOAL.md — согласованная цель, границы и критерии приёмки.
- STATUS.md — текущее состояние, фактические проверки, блокеры и следующий шаг.
- plans/ — отдельный согласованный план на каждую итерацию.
- reports/ — отчёты реализации, тестов, запуска и аудита.
- README.md — фактические команды установки, запуска, тестов и сборки.

Если GOAL.md содержит только шаблон, сначала уточни требования и дождись
подтверждения. Не выдумывай согласованные решения. Подготовить пустой каркас
можно по отдельному запросу. Не заполняй STATUS.md предположениями об успехе.

## Технические рамки

- HTML/CSS и JavaScript, Vite; Vitest для логики, Playwright для браузерных тестов.
  Без React, backend, аккаунтов, внешних API и ключей.
- Данные и фотографии проектов используются после согласования источников.
- Отделяй логику поиска и фильтрации от DOM для независимой проверки.
- Сохранение добавляй только в рамках согласованной итерации. Для localStorage
  используй отдельный ключ проекта; не очищай хранилище целиком.
- Избегай лишних зависимостей. Новые зависимости вне плана согласуй.
  Команды сверяй с package.json и записывай в README.

## Проверки и завершение

- Проверяй критерии из плана, пустые результаты и сочетания фильтров и прежнее поведение.
  Для сохранения проверяй перезагрузку страницы.
- Не отключай тесты и не подменяй ожидаемый результат ради успешного прогона.
- Записывай фактические команды и результаты в отдельную папку прогона reports/.
  Существующие отчёты сохраняй. После изменений выполняй проверки заново.
- Различай «реализовано», «тесты написаны», «проверено» и «принято пользователем».
  Если проверка не выполнена, укажи причину. Не утверждай, что внешний вид проверен,
  если его не смотрели в браузере.
- После успешных автоматических проверок предложи короткий сценарий ручной
  приёмки. Её результат записывай только после фактической проверки пользователем.

Не меняй согласованные требования, инструкции ролей и скиллы ради исправления
приложения. Не затрагивай чужие изменения. При противоречии или нехватке доступа
сообщи конкретную проблему и необходимое решение.

Commit, push, создание репозитория и deploy не выполняй автоматически.
